# U5 — 가설 생성 H1. 검색 **전에** 무엇을 찾을지 정한다

## 왜

지금은 수집이 need 와 무관하게 전부 돈다. 그래서 S6(확인 판정)이 "무엇을
확인해야 하는가"를 모르고, S9(구조 픽)가 "무엇이 충족됐나"로 고를 수 없다.
지시문이 **"이게 페이블 순서의 핵심"** 이라고 적은 자리다.

```
재현:
  app/engine/hypothesis.py 가 없다
  pick_ledger 에 hypothesis 칸이 없다 — 무엇을 찾기로 했는지 나중에 못 본다
```

## 설계 — 게이트가 방향을 정하고, 방향이 need 를 정한다

```
입력   gate(라벨·gap·side) · sport · bigmatch
출력   {direction, need[], sufficient_count}
```
- **시장 과대**: 시장이 그쪽을 높게 본다 → **반대편을 세울 근거**를 찾는다.
  (약팀 쪽 결장이 없는가 · 강팀 쪽 피로·로테이션이 있는가)
- **가치 의심**: 우리가 높게 본다 → **우리 쪽을 무너뜨릴 근거**를 찾는다.
  못 찾으면 사전값이 틀린 것이다.
- **동의**: 승패는 볼 것이 없다 → **파생(U/O·핸디)** need 만.
- **보드 고정**: need 없음. 수집도 하지 않는다.

🔴 `sufficient_count` 는 "이만큼 확인되면 픽으로 간다"는 **문턱**이다.
   빅매치는 3(자료가 많아 우연 일치가 쉽다), 그 외는 2.

## ① 이 함수/상태를 읽는 곳 **전부**

```
(신규) hypothesis.build   ← U6 표적 수집이 need 를 받아 쓴다
                          ← U7 confirm(need, collected)
                          ← 원장 pick_ledger.hypothesis (JSON)
gate.Verdict              ← 입력(라벨·side)
bigmatch.is_big_match     ← 입력
```

## ② 깨뜨릴 수 있는 기존 동작

- 🔴 **순수 함수다.** DB·HTTP 를 부르지 않는다 — `gate.py` 와 같은 규칙.
  계약이 import 를 전수로 본다.
- 🔴 need 이름은 **S5 가 수집하는 항목 이름과 같아야 한다.** 두 이름표를
  만들면 U7 이 영영 못 맞춘다. 지금은 S5 추출 스키마(out·doubt·xi_status·
  xi·bench_notable·last3·midweek·notes)를 **원본**으로 쓴다.
- ⚠️ 이 U 는 **need 를 만들기만 한다.** 수집을 need 로 좁히는 것은 U6,
  확인 판정은 U7 이다. 한 U 한 변경.
- ⚠️ 원장 칸을 늘린다(`hypothesis JSONB`). 스키마 변경이므로 스케줄러를
  먼저 배포해야 한다(기동 시 적용).

## ③ 되돌리기
