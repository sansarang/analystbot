# GM-4 — 같은 소스의 다른 경기 id 를 같은 경기로 합쳤다

## 왜

실사고 2026-09-13. 오늘 13:30 JST 소프트뱅크 경기가 DB에 안 들어가고 **어제
18:00 행이 갱신**됐고, 봇이 그 행을 판정했다. 사용자 지적: *"빗나간 게 아니라
봇이 어제(9/12) 경기를 판정한 겁니다. 판단이 갈린 게 아니라 입력이 틀렸어요."*

```
Yahoo 원문 2026-09-13   2021039419  지바롯데@소프트뱅크 13:30 scheduled
DB                      yahoo:20210394**14**  09-12 09:00Z (KST 18:00)
간격 19.5h → MATCH_WINDOW_HOURS=20 안 → 같은 경기로 봤다
```

`_FIND` 는 **ext_id 를 보지 않는다**(종목·홈·원정·시각창만). 그 설계 의도는
"소스가 달라 ext_id 가 다른 **같은 경기**"를 잇는 것이다(실사고 2026-08-27:
`odds:…` 행과 `kbo:…` 행이 남남이라 채점이 막혔다). 그런데 **같은 소스의 다른
id** 는 정반대 — 연전의 다음 경기다.

## ① 읽는 곳 전부
```
$ grep -rn "apply_result" app/
game_match.py 정의 · yahoo_npb.upsert_schedule · yahoo_npb.upsert_final_scores
naver_kbo(결과) · odds(이벤트) 등 결과·일정 적재부
_FIND 를 쓰는 곳은 apply_result 하나
```

## ② 상태
| 상태 | 성격 |
|---|---|
| `_FIND` SQL | **같은 소스 다른 id 를 후보에서 뺀다** |
| `apply_result` | `ext_id` 를 `_FIND` 에 넘긴다 |
| `MATCH_WINDOW_HOURS` | **그대로 20h** — 창을 좁히면 순연·시각정정을 놓친다 |

🔴 **소스가 다른 병합은 건드리지 않는다.** 그것이 이 모듈의 존재 이유다.
   가르는 기준은 `ext_id` 의 **접두사(소스)** 다: 같으면 다른 경기, 다르면 병합.

## ③ 분기
종목 분기 없음. SQL 한 절이다.

## ④ 조용히 실패하는가
| 위험 | 대응 |
|---|---|
| 🔴 **소스 간 병합이 깨져 채점이 막힌다** ← 가장 큰 반대 위험 | 다른 접두사는 계속 갱신되는지 계약(2026-08-27 실사고 재현 방지) |
| 접두사가 없는 ext_id | `split_part` 는 구분자가 없으면 전체를 돌려준다 — 같은 값일 때만 배제되므로 무해 |
| 창을 좁혀 순연을 놓친다 | 창을 **안 건드린다** |
| 또 조용히 합쳐진다 | `_FIND` 에 가드가 있는지 계약 |

⚠️ 못 잰 것: 고친 뒤 오늘 소뱅 경기가 **새 행**으로 들어가는가.
   운영에서 `upsert_schedule` 재실행으로 잰다.

## ⑤ 사본
- 창 상수를 새로 만들지 않는다. `MERGE_WINDOW_HOURS` 도 건드리지 않는다.
