## 1. 영향 지도 5문

**① 어디를 만드나.**

| 파일 | 무엇 |
|---|---|
| `tools/backfill_results.py` (신규) | 날짜 범위를 훑어 `upsert_slate` 로 적재 |
| `app/collectors/fotmob.py` | `upsert_slate(..., rows=None)` — 미리 받은 목록을 넘길 자리 |

**② 왜 `rows=` 가 필요한가.** FotMob 하루치 목록은 **한 번 받으면 전 리그가
들어 있다**(541경기). 리그마다 `slate()` 를 다시 부르면 요청이 4배가 된다.
날짜당 1회 받고 4리그가 나눠 쓴다.

**③ 규칙은 어디에 한 번만 두나.** 적재 규칙(팀 매칭·점수 coalesce·conflict·
`apply_result`)은 전부 `upsert_slate` 그대로다. 이 도구는 **날짜를 돌리기만**
한다 — 새 적재기를 만들지 않는다.

**④ 무엇이 깨질 수 있나.**
- 🔴 **차단당하는 것**이 최대 위험이다. 요청 간격 2초는 `fotmob._pace` 가 이미
  강제한다(`MIN_GAP_SEC=2.0`). 그 위에 **빈 응답이 이어지면 즉시 멈춘다** —
  실제 날짜는 언제나 경기가 있으므로 연속 빈손은 차단 신호다.
- 🔴 **`--dry-run` 이 기본**이다. 쓰기는 명시해야 한다.
- ⚠️ 원본 JSON 을 날짜별로 캐시한다 — 같은 날을 다시 받지 않는다(지시문).
- ⚠️ 이름을 못 붙인 경기는 `upsert_slate` 이 이미 **행을 만들지 않고** 로그를
  남긴다(FMR-1 규약). 소급이라고 느슨해지지 않는다.

**⑤ 틀렸을 때 알려줄 테스트.** `tests/test_w3_4_backfill.py` — 도구 존재 ·
dry-run · `rows=` 인자 · **넘긴 목록을 쓰면 다시 안 받는가** · 빈 응답 중단 ·
dry-run 이 DB 에 쓰지 않는가.

## 2. 범위 (지시문 "리그별 개막일~어제")

⚠️ **각 리그의 진짜 개막일을 우리는 모른다** — 그 값을 주는 소스가 없다.
   지어내지 않고 `--days N`(기본 60)으로 둔다. 우리 `games` 의 가장 이른
   경기가 2026-08-23 이므로 60일이면 그보다 앞까지 덮는다.
