# SRCH-7 — 판정이 필요한 것을 받아 온다. DB 우선, 없으면 검색.

사용자 지시 2026-09-12: "양팀 선발의 상세 투구는 있다.. 없으면 안트로픽이나
퍼플릭스한테 요청을 해서 받으라고 해야 한다.. 제미니는 필요한 거를
재요청할 수 있다"

## 왜

SRCH-6 으로 제미니가 분석글을 쓰게 했더니 **4/4 전부** 이렇게 끝났다:

```
"다만 양 팀 선발 투수의 최근 등판 이닝과 실점 세부 기록이 확인되지 않은
 점은 변수입니다."                                       (NC@두산)
"다만 양 팀 선발 투수의 최근 상세 성적과 구체적인 투구 내용을 확인하지
 못한 점은 변수로 남아 있습니다."                         (LG@삼성·롯데@키움)
"다만 선발 투수 네일과 대니엘의 최근 세부 투구 성적을 확인하지 못한
 점은 변수로 남아 있습니다."                              (KIA@KT)
```

**그 기록은 우리 DB에 있다** — `dbref.ITEMS` 의 `선발 최근 등판`.
그런데 판정 프롬프트가 이렇게 막고 있었다:

```
🔴 여기 있는 것이 전부다. 우리 DB(최근 3경기·팀 폼·레이팅·불펜·타순)는
   이 자리에 오지 않는다.
```

DB 참조는 판정 **뒤**(4단계)였다. 순서가 거꾸로다.

그리고 2단계 선별은 이미 정확히 지목하고 있었다 — 실측 3경기 전부
`DB요청: 선발 최근 등판`. **그 칸을 아무도 읽지 않았다.**
ORD-15 에서 "AI 에게 전량을 주고 자율로 고르게" 바꾸며 키워드 매칭을
걷어냈고, 그때 `DB요청` 이 죽은 칸이 됐다. 만들어 놓고 안 쓴 것이다
(이 저장소의 반복 결함 PGP-2).

## ① 이 함수/상태를 읽는 곳 **전부**

```
$ grep -rn "DB요청" app/engine/*.py | grep -v prompts.py
app/engine/triage.py:125   "DB요청": [...]        ← 만들기만 한다
app/engine/dbref.py:6      (주석에서 옛 방식을 설명)
   → **읽는 운영 코드가 0 이다.**

$ grep -rn "verdict.decide\|dbref\." app/
app/engine/matchup.py  v = await verdict.decide(...)   ← 유일한 호출부
app/engine/matchup.py  ref = await dbref.recheck(...)  ← 유일한 호출부
```

새로 만드는 `dbref.fetch` 를 읽는 곳은 `_judge_v3` 하나다.
`dbref.bundle`·`ITEMS` 는 **그대로 둔다** — `recheck`(4단계)가 계속 쓴다.

빌려 쓰는 원본:
| 무엇 | 원본 |
|---|---|
| DB 항목 목록·페이로드 | `dbref.ITEMS` · `dbref.bundle` |
| 행 모양 | `gather._row` (계약이 키 집합 대조) |
| 검색 | `gather.search` (SRCH-3·4) |
| 질문 상한 | `websearch.MAX_ASKS` |

## ② 만드는/바꾸는 상태

| 상태 | 성격 | 다른 곳이 다른 규칙으로 갱신하나 |
|---|---|---|
| `dbref.fetch()` | 새 함수 (읽기 전용) | 아니다 |
| `JUDGE2` 의 `추가요청` | 출력 칸 추가 | 아니다 |
| `verdict.decide()["추가요청"]` | 반환 키 추가 | 아니다. 읽는 곳은 `_judge_v3` |
| `tri["채택"]` 에 DB 행을 **합친다** | 기존 리스트 확장 | 🔴 아래 |
| `order_v3["DB보충"·"재판정"]` | 원장 키 추가 | 아니다 |

🔴 **`채택` 에 DB 행을 합치는 것이 위험이다.** 4단계 `dbref.recheck` 가
   같은 `채택` 을 읽으므로 **같은 DB 내용을 두 번** 보게 된다.
   → 해롭지 않다(같은 사실이다). 다만 `계측.채택` 은 덮지 않고
     `DB보충` 으로 따로 센다 — 두 숫자가 같은 것을 세는 척하면 상태 이원화다.
   ⚠️ `recheck` 가 "이미 봤다"고 승자를 덜 바꿀 수 있다. 그건 관측할 일이고,
     `승자변경` 건수가 이미 로그에 남는다.

## ③ 리그·종목·경로 분기

**생기지 않는다.** `_judge_v3` 는 kbo·npb·mlb 공통이고 `dbref.ITEMS` 도 공통이다.
축구는 이 경로를 타지 않는다.

⚠️ 종목마다 **채워지는 항목 수가 다르다** — 실측 2026-09-12 KBO/NPB 는
   9종 중 3~6종만 있었다. 그건 분기가 아니라 `bundle` 의 `없음` 으로
   이미 드러난다. 없는 것은 `fetch` 가 행을 만들지 않는다(계약).

## ④ 조용히 실패하는가

| 위험 | 대응 |
|---|---|
| 🔴 **재요청이 습관이 되어 호출이 두 배** | **1회로 묶는다.** `verdict.decide` 호출이 정확히 2회인지 계약으로 단언 |
| 🔴 **DB에 있는 것을 유료로 다시 산다** | DB 로 먼저 채우고 **못 채운 것만** 검색. 계약이 순서를 단언 |
| 이름을 못 알아들어 조용히 버린다 | `with_miss=True` 로 못 맞춘 이름을 돌려주고 로그에 남긴다. 실측 전례(4경기 중 2경기 매핑 실패)가 근거 |
| 값이 빈 항목을 실어 "있다"로 읽힌다 | 값이 없으면 행을 만들지 않는다(계약) |
| 보충했는데 판정이 그대로다 | `재판정` 여부와 전후 승자를 원장·로그에 남긴다 |
| 프롬프트의 옛 문구("DB는 오지 않는다")가 남는다 | 그 문자열의 부재를 계약으로 단언 |

⚠️ **아직 못 재는 것**: 보충이 판정을 더 낫게 하는가. 이번 합격 기준은
   "필요한 것을 받는다 · 다시 묻는다 · 공짜를 먼저 쓴다"까지다.

## ⑤ 이미 있는 사실을 다시 적는가

- DB 항목 이름을 프롬프트에 **다시 적지 않는다** — `dbref.ITEMS` 에서
  생성해 넣는다. 손으로 옮기면 항목이 늘 때 프롬프트만 옛것이 된다.
- 질문 상한은 `websearch.MAX_ASKS` 하나. 새 상수를 만들지 않는다.
- 행 모양·검색 경로·확신 눈금 전부 기존 원본을 부른다.
