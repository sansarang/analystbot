# SRCH-3 — 검색 요청자를 2단계 선별로 옮긴다. 그리고 배선을 못 박는다.

사용자 지시 2026-09-12: "최종 판정 2단계는 삭제..1단계로 제미니 최종 판정으로
간다" · "퍼플릭스와 안트로픽" · "경기당 1회 질문 3개로 해라"

## 왜

SRCH-1 이 2차 검증을 지웠는데, **검색을 요청하던 것이 그 2차 검증관**이었다.
지금 이 경로의 외부 검색은 0 이고, SRCH-2 가 만든 `websearch.ask` 를
**아무도 부르지 않는다.**

선별(2단계)은 이미 `없는것` 을 돌려준다(`triage.py`). 요청자는 거기 있으면
된다 — 새 개념을 만들지 않는다. 바뀌는 흐름:

```
전  수집 → 선별 → 판정 → DB참조
후  수집 → 선별(+검색질문) → **검색** → 판정 → DB참조
```

## ① 이 함수/상태를 읽는 곳 **전부**

```
$ grep -rn "triage.run\|verdict.decide\|gather.collect" app/ tools/
app/engine/matchup.py:  tri = await triage.run(...)      ← 유일한 호출부
app/engine/matchup.py:  v = await verdict.decide(...)    ← 유일한 호출부
app/engine/matchup.py:  col = await gather.collect(...)  ← 유일한 호출부
$ grep -rn "websearch" app/
app/collectors/websearch.py   (자기 자신뿐 — 부르는 곳이 0 이다)
```

`triage.run` 의 반환에 키를 하나 더한다(`검색요청`). 읽는 곳은
`matchup._judge_v3` 하나뿐이고, 나머지 키는 그대로다 — **기존 키를 바꾸지
않으므로** 종전 독자는 영향이 없다.

`gather.search` 는 새 함수다. `gather.collect` 를 건드리지 않는다 —
수집(무료)과 검색(유료)은 **다른 시점, 다른 지갑**이다.

## ② 만드는/바꾸는 상태

| 상태 | 성격 | 다른 곳이 다른 규칙으로 갱신하나 |
|---|---|---|
| `triage.run()["검색요청"]` | 반환 키 추가 | 아니다. 읽는 곳은 `_judge_v3` 하나 |
| `order_v3["검색요청"·"검색n"·"검색출처"]` | 판정 원장 | `persist_matchup_record` 가 통째로 저장. 읽는 쪽은 전부 `.get` |
| `tri["채택"]` 에 검색 행을 **합친다** | 기존 리스트 확장 | 🔴 여기가 위험하다 — 아래 |

🔴 **`채택` 에 합치는 것이 이 수정의 핵심이자 위험이다.**
   판정(`verdict.decide`)과 DB참조(`dbref.recheck`)가 같은 `채택` 을 읽는다.
   검색 행을 합치면 **둘 다** 그것을 본다 — 의도한 것이다(검색해 놓고 판정이
   못 보면 돈만 쓴 것). 다만 `계측.채택` 은 선별이 센 숫자라 **합친 뒤와
   어긋난다.** 그래서 검색분은 `검색n` 으로 **따로** 남기고 `계측` 을 덮어쓰지
   않는다. 두 숫자가 같은 것을 세는 척하면 그게 상태 이원화다.

## ③ 리그·종목·경로 분기

**생기지 않는다.** `_judge_v3` 는 kbo·npb·mlb 공통이고 검색도 공통이다.
축구는 이 경로를 타지 않는다(구 Judge).

⚠️ 이번 단계에서 배선하는 채널은 **Anthropic 하나**다. 퍼플렉시티는
   SRCH-4 에서 **같은 날짜 게이트를 붙여** 같은 `gather.search` 안에 더한다.
   게이트 없이 먼저 붙이면 SRCH-2 가 막은 결함(5개월 전 기사)을 다시 연다.
   → `gather.search` 는 처음부터 **채널 여러 개를 병렬로 돌리는 모양**으로
     쓴다. SRCH-4 가 한 줄을 더하면 끝나도록.

## ④ 조용히 실패하는가

| 위험 | 대응 |
|---|---|
| 🔴 **만들었는데 안 불린다** (이 저장소 반복 결함 PGP-2·SCT-1) | `_judge_v3` 본문을 읽어 `search` 가 **선별과 판정 사이**에 있는지 단언. `app/` 안에 `websearch` 호출부가 존재하는지도 단언 |
| 검색해 놓고 판정이 못 본다 | `verdict.decide` 에 넘어간 `채택` 에 검색 행이 있는지 단언 |
| 습관적 요청으로 경기당 $0.10 고정 | 요청 0개면 **호출 0** 을 단언. 프롬프트에도 "돈이 든다"를 적는다 |
| 검색 0건인데 "검색 안 함"으로 보인다 | `검색요청`·`검색n`·`검색출처` 를 원장에 따로 남긴다. 요청 2·결과 0 이 구분된다 |
| 검색 실패로 카드가 0장 | `search` 는 예외를 삼키고 빈손을 돌려준다. 판정은 계속된다(단언) |
| `계측.채택` 과 실제 채택 수가 어긋난다 | 위 ②항 — 덮어쓰지 않고 `검색n` 으로 분리 |
| 질문이 성적 조회로 채워진다 | 프롬프트에 금지. ORD-5 실측(38문 중 28문이 성적)이 근거 |

⚠️ **아직 못 재는 것**: 검색이 판정을 실제로 바꾸는가. 이번 단계의 합격
   기준은 "배선이 이어졌다 · 재료에 들어갔다"까지다. 승패가 바뀌는지는
   같은 경기를 검색 on/off 로 돌려 비교해야 하고, 그건 배포 뒤 실측이다.
   **지금 "좋아졌다"고 말하지 않는다.**

## ⑤ 이미 있는 사실을 다시 적는가

- 질문 상한 3은 `websearch.MAX_ASKS` 가 원본이다. `triage.MAX_ASKS` 는
  그것을 **임포트해서 쓴다** — 숫자를 두 번 적지 않는다.
- 행 모양은 `gather._row` 원본 그대로. 검색 행도 같은 모양이라 `채택` 에
  그냥 합쳐진다(새 계약 없음).
- 채널 스위치는 `config` 가 원본. `gather.search` 는 스위치를 보지 않는다 —
  각 채널이 자기 스위치를 본다(`websearch._enabled`).
- 오늘(KST)은 `deepsearch._today_kst` 하나.
