# PA-16 — U9 시장 흐름이 절반만 배선됐다

## 왜

U9 는 `odds_move` 에 넷을 더했다 — `STEAM`(3북 이상 같은 방향 3%p) ·
`book_disagree`(북별 SD > 2%p) · `line_to_pp`(핸디 0.5 = 4%p) · `adj_confirm`.
그런데 `pick_ledger.record_move` 는 여전히

```python
mv = M.classify(move_pp=pp, news=news)      # ← n_books 를 안 넘긴다
await conn.execute(_MOVE_SAVE, game_id, o_open, mv.label, mv.reason)
```

만 했다. 재현 4건:
```
· record_move 가 classify 에 n_books 를 안 넘긴다 — steam 이 영원히 안 뜬다
· market_flow 칸에 쓰는 코드가 없다 (PART A 실측 0/2경기)
· odds_move.book_disagree 를 부르는 코드가 app/ 전체에 0건
· odds_move.adj_confirm 를 부르는 코드가 app/ 전체에 0건
```
계산 자체는 정확하다(전제 확인):
```
classify(n_books=3, 4%p) → steam · "4.0%p 이동 · 3북 동시 — 시장 전체가 밀렸다"
book_disagree([50,56,62]) → {'sd_pp': 4.9, 'disagree': True, 'n': 3}
```

🔴 **같은 병 일곱 번째다** — analyze · gate.select · U9 · U10 · book_gap ·
   예산 · 이번. 만들고 안 이었다.

## ① 이 함수/상태를 읽는 곳 **전부**

```
odds_move.classify(move_pp, news, n_books)  ← 5분류 원본
odds_move.book_disagree / adj_confirm       ← 호출 0건이었다
odds_move.STEAM / MONEY / CONTRA            ← 라벨 원본. 베끼지 않는다
pick_ledger.record_move                     ← 고치는 곳
  ├ _MOVE_SNAP_SQL → _snap_probs            ← 북·시점별 확률. 이미 있다
  └ _MOVE_SAVE                              ← market_flow · flow_class 추가
pick_ledger.adj_pp                          ← adj_confirm 의 입력(합계)
db/schema.sql market_flow · flow_class      ← 이미 있다(U13·U10에서 추가됨)
```

## ② 깨뜨릴 수 있는 기존 동작

- 🔴 **저장 전용이다.** `adj_confirm` 이 `cancel`·`stake_mult` 를 내지만
  **여기서 픽을 취소하거나 판돈을 줄이지 않는다** — 그건 발송 규칙(조건 B)의
  몫이고 별도 단위다. 계약이 그 경계를 잰다.
- 🔴 **북 수를 모르면 종전대로다.** `n_books` 가 None 이면 `classify` 는
  4분류만 낸다. 없는 정보로 더 센 라벨(steam)을 붙이지 않는다.
- 🔴 **같은 시점(snap_tag)의 북만 센다.** 시점이 다른 값을 섞으면 "동시에
  밀렸다"가 거짓이 된다.
- 🔴 **`move_class` 를 바꾸지 않는다.** `flow_class` 는 같은 값을 U13 칸에
  복제할 뿐이고, 종전 소비자는 그대로 `move_class` 를 읽는다.
- ⚠️ steam 이 처음으로 뜰 수 있다 — 종전에는 구조적으로 불가능했다.
  첫 사이클에서 분류 분포를 봐야 한다.
- ⚠️ `line_to_pp`(핸디 환산)는 **이 단위에서 안 쓴다.** 파생 시장 스냅샷이
  전제라 U10/PA-17 과 함께 가는 것이 맞다.
