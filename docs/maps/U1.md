# U1 — 트리거 8종 추가(13종) · 창 ±30h · ingest_gap

## 왜

지금 트리거는 **스냅샷 5종뿐**이다(`triggers.KINDS`). S4~S11 이 붙을 시각이
없다. 그리고 `ingest_gap` 이 없어서 **J1·K리그1·ACL 이 18일간 0건**이어도
아무도 몰랐다(P2-0 — 차단기가 2026-08-27 에 내려간 뒤 09-14 까지).

```
재현:
  트리거가 5종뿐 — ['open','pre','lineup','late','close']
  행동 트리거(ACTIONS) 없음
  슬레이트 창이 now−6h ~ now+30h  (−30h 여야 한다)
  ingest_gap 없음
```

## 🔴 KINDS 에 그냥 넣으면 안 된다

`triggers.py:18` 이 명시한다 — "스냅샷 5시점. 이름은 Part 1-B-1 의 `snap_tag`
와 **같다** — 두 이름표를 만들면 대조가 깨진다."
`_triggers_tick` 은 발사할 때 `_TRIGGER_TAG_SQL(game_id, kind, since)` 로
**kind 를 그대로 snap_tag 에 넣는다.** 여기에 `model`·`rejudge` 를 넣으면:
  · `snap_tag='rejudge'` 같은 행이 생기고
  · `odds_move.BASELINE_ORDER` 에 없는 이름이라
    `pick_ledger.record_move` 의 `order.index()` 가 **ValueError** 로 터진다
    (이동 분석이 통째로 죽는다 — SNAP-1 에서 잠근 바로 그 위험).

→ **`KINDS`(스냅샷 5) 와 `ACTIONS`(행동 8) 를 나눈다.** `plan()` 은 둘을 합친
  `ALL_KINDS`(13) 로 계획하고, **이름표는 `KINDS` 인 것만** 붙인다.

## ① 이 함수/상태를 읽는 곳 **전부**

```
triggers.KINDS      ← plan() · scheduler._triggers_tick(kind → snap_tag)
                    ← odds_move.BASELINE_ORDER 와 이름이 같아야 한다
                    ← tests/test_snap1_open_tag.py (set(KINDS) <= BASELINE_ORDER)
triggers.plan       ← _triggers_tick ①계획
_TRIGGER_PLAN_SQL   ← 창 (now−6h, now+30h)
_TRIGGER_TAG_SQL    ← 발사 시 이름표
scheduler._triggers_tick  ← triggers_1m 잡(1분)
```

## ② 깨뜨릴 수 있는 기존 동작

- 🔴 **이름표에 행동 kind 가 새면 이동 분석이 죽는다**(위). 계약이
  `set(KINDS) <= BASELINE_ORDER` 와 "행동 kind 는 태그하지 않는다"를 잠근다.
- 🔴 트리거가 13종이 되면 경기당 행이 2.6배다. `DUE_SQL LIMIT`·
  `MAX_CONCURRENT` 는 그대로 두고, **행동 트리거는 지금 아무 일도 하지
  않는다**(자리만 만든다 — U5~U11 이 붙인다). 그 사실을 로그가 말한다.
- 🔴 창을 −30h 로 넓히면 **끝난 경기까지 계획 대상**이 된다. `plan()` 은 지난
  시점도 남기고 `DUE_SQL` 이 쏘므로, 오래된 경기가 한 번에 발사될 수 있다.
  → `_TRIGGER_PLAN_SQL` 은 `status='scheduled'` 만 본다(기존 조건 유지 확인).
- ⚠️ `ingest_gap` 은 **경고만** 한다. 자동 복구하지 않는다(차단기와 같은 태도).
