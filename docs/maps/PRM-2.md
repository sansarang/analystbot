# PRM-2 — 채택 자료 300자 절단이 DB 행의 원정 블록을 통째로 잘랐다

## 왜

실측 2026-09-13 (운영, Seattle Mariners @ Athletics, game 6003). 제미니가
"원정 선발 Bryan Woo의 최근 등판 기록을 확인하지 못했다"를 세 번 반복했다.
자료는 **전부 있었다**:

```
운영 DB          Bryan Woo 등판 5건 (9/6 8.0이닝 … 8/11 5.0이닝)
payload          home 5건 · away 5건 · 키 동일
dbref.bundle 행  1331자 (ITEM_MAX 2600 → 잘림 없음)
최종 프롬프트     3992자 · '선발등판' **1회**   ← 두 블록이면 2회여야 한다
분리 실험        "복사만 해라" → {"복사": "없음"}  ← 정말 없었다
```

범인은 `verdict.fmt_kept` 의 행당 300자 절단이다:
```python
" ".join(str(r.get("답") or "").split())[:300]
```
그 상한은 **뉴스 기사 한 줄** 기준인데 DB 행(1331자)이 같은 줄로 들어가
`{"home": {...Gage Jump...}` 까지만 남고 `"away"` 가 사라졌다.

⚠️ 내가 앞서 PRM-1 로 라벨을 붙인 것은 **자리를 잘못 짚은 수정**이었다.
   잘리는 곳은 `dbref` 가 아니라 `verdict` 였다.

## ① 읽는 곳 전부
```
verdict.fmt_kept  ← verdict.render 한 곳에서만 쓴다
채택 행의 출처: gather(뉴스·위성) · dbref.fetch(DB) · gather.search(유료검색)
DB 행의 소스 라벨 원본: dbref.SOURCE
```

## ② 상태
| 상태 | 성격 |
|---|---|
| `fmt_kept` 의 상한 | 행의 **소스에 따라** 나뉜다 |
| 뉴스·검색 행 | **300자 그대로** |
| DB 행 | `dbref.ITEM_MAX`(2600) — **원본 상수를 그대로 쓴다** |

🔴 숫자를 두 곳에 적지 않는다 — DB 행의 길이 원본은 `dbref.ITEM_MAX` 다.
🔴 뉴스 행 300자를 건드리지 않는다. 기사 한 줄에 맞춘 값이고 프롬프트가 부푼다.

## ③ 분기
종목 분기 없음. **행의 소스**로만 가른다.

## ④ 조용히 실패하는가
| 위험 | 대응 |
|---|---|
| 🔴 프롬프트가 부푼다 | DB 행은 경기당 2~3개뿐이고 각 2600 상한. 뉴스 행은 불변(계약) |
| 🔴 또 조용히 잘린다 | DB 행에 원정 블록이 남는지 계약으로 단언 |
| 소스 라벨이 달라 못 알아본다 | `dbref.SOURCE` 를 그대로 비교. 라벨 없으면 뉴스로 본다(계약) |
| DB 행도 무한이 된다 | `ITEM_MAX` 상한 계약 |

⚠️ 못 잰 것: 고친 뒤 제미니가 원정 선발을 실제로 인용하는가.
   **같은 경기 재분석으로 잰다.** 안 되면 그렇게 보고한다.

## ⑤ 사본
- 길이 상수를 새로 만들지 않는다 — `dbref.ITEM_MAX`.
- 소스 라벨을 새로 정하지 않는다 — `dbref.SOURCE`.
