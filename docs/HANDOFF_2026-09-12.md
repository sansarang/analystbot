```
  · 제미나이가 판정·서술하고 · 제미나이가 DB를 참조한다.
새 구조를 만들지 마라. 야구가 쓰는 그 경로에 축구를 태운다.

코드가 꼬이지 않게 **종목별로 갈리는 것을 표로 먼저 빼고** 축구를 행으로
더한다. `if sport == "soccer"` 분기를 엔진에 흩지 마라.
```

**왜 이 전제인가** — v3 엔진(`gather`·`triage`·`verdict`·`dbref`·`_judge_v3`)은
**모양은 공통인데 내용이 야구 전용**이다. 축구를 그냥 끼우면 분기가 엔진 전체에
번지고, 그때부터 야구를 고칠 때마다 축구가 깨진다(그 반대도). 오늘 여덟 단계로
겨우 세운 경로를 축구가 흔들면 안 된다.

---

### 1단계 — 조사만, 코드 수정 금지

```
축구를 v3 경로에 태우려면 네 축(위성·제미니·퍼플렉시티·안트로픽) 각각에
무엇이 필요한지 전수로 조사해라. 코드 수정하지 말고 표로 보고해라.
반드시 포함할 것:
  · 리그 7개별 자료 가용성 (일정·배당·Elo·xG·라인업) — 어디까지 다룰지 정해야 한다
  · 위성 축구 어댑터를 무엇으로 만들 것인가 (소스 후보와 각각의 수율 추정)
  · dbref.ITEMS 9종 중 축구에 쓸 수 있는 것과 새로 필요한 것
  · 3-way(승/무/패)를 어디서 어떻게 처리할지 선택지 — 비용·위험과 함께
```

**왜 조사부터인가** — 오늘 가장 크게 튄 실수가 "만들어 놓고 안 불린다"였다.
`websearch.ask` 도, `DB요청` 칸도 그랬다. **무엇이 이미 있고 무엇이 없는지
세지 않고 만들면** 이미 있는 것을 다시 만들거나, 만든 것이 경로에 안 닿는다.
그리고 3-way 는 `verdict.decide` 의 반환 모양을 바꾸는 일이라 **나중에 고치면
그 위에 쌓은 것을 전부 다시 만져야 한다.** 설계 결정을 먼저 받아야 한다.

---

### 2단계 — 분류 (야구 회귀 0)

```
종목별로 갈리는 것을 registry 표로 빼라. 축구는 아직 넣지 마라.
야구가 그대로 도는 것을 실측으로 증명한 뒤에 보고해라.
```

**왜 축구를 아직 안 넣나** — 두 가지를 한 번에 바꾸면 **무엇이 깨뜨렸는지 못
가린다.** 표로 빼는 것만으로도 야구가 깨질 수 있다(`gather.collect` 의 jobs,
`dbref.ITEMS`, 프롬프트 어휘가 전부 움직인다). 야구 회귀 0 을 먼저 증명해
두면, 다음 단계에서 뭔가 깨졌을 때 **범인이 축구라는 것이 확실해진다.**
오늘 여덟 단계를 그렇게 돌려서 매번 원인이 한 개였다.

---

### 3단계 — 위성 축구 어댑터

```
축구 위성 어댑터를 만들어라. ScoutSport 도 켜라.
실제 경기로 몇 건이 들어오고 그중 몇 건이 **그 경기 것**인지 전수로 세어
보여줘라 (야구는 33~67% 였다).
```

**왜 위성이 먼저인가** — 위성이 v3 수집의 **주력**이다(야구 경기당 12건).
그리고 오늘 실측이 보여준 것: **위성이 오늘 소식을 공짜로 다 가져오면
유료 검색이 0건**이 된다(KBO 4경기 전부). 위성이 비면 반대로 2단계가 거를
것이 없어 검색에 의존하게 되고, 그러면 경기당 $0.10 이 고정된다.
**위성의 수율이 이 파이프라인의 비용을 결정한다.**

**왜 전수로 세라고 하나** — 야구 위성은 팀 이름 키워드로 붙어서 **무관한 기사가
33~67%** 섞였다. 제미니가 걸러 주긴 하지만, 몇 %가 쓰레기인지 모르면
"제미니가 잘 거르는 것"과 "애초에 깨끗한 것"을 구분할 수 없다.

---

### 4단계 — 제미니 3자리 (선별·판정·DB참조)

```
축구 프롬프트 어휘를 채우고 제미니를 붙여라.
실제 경기로 갈림길·채택·기각을 뽑아 보여줘라. 기각 사유까지.
```

**왜 기각 사유까지 보라고 하나** — 오늘 그걸 봐서 **제미니의 거르기가 정확하다는
것을 확인**했다(손으로 센 것과 채택 수가 거의 일치). 동시에 결함도 찾았다 —
중복 제거가 **정보가 더 많은 쪽을 버렸다**(구자욱 담 증세 기사). 채택 수만 보면
둘 다 안 보인다.

**왜 제미니 사슬은 안 건드리나** — `JUDGE_CHAIN` 은 종목을 모른다. 바꿀 것은
**프롬프트 어휘뿐**이다("선발투수·타순·이닝" → 축구 어휘). 사슬을 건드리면
야구 판정이 같이 흔들린다.

---

### 5단계 — 안트로픽·퍼플렉시티 배선

```
2단계 선별과 판정이 요청했을 때 안트로픽·퍼플렉시티가 답을 가져오는지
실제 경기로 확인해라. 날짜 게이트가 축구에서도 걸리는지 함께 봐라.
```

**왜 날짜 게이트를 따로 확인하나** — 게이트가 없으면 **5개월 전 기사를 오늘
일로 인용한다**(구자욱 건에서 실제로 그랬다). 축구는 **리그별로 경기 간격이
길어**(주 1~2회) 야구보다 오래된 기사가 더 그럴듯해 보인다. 허용 나이
`MAX_AGE_DAYS=3` 이 축구에 맞는지는 **아직 안 쟀다** — 여기서 재야 한다.

**왜 배선만 하면 되나** — 퍼플렉시티는 `deepsearch_sports` 에 이미 `soccer` 가
있고, 안트로픽 `websearch` 는 질문만 받아 **종목을 모른다.** 새로 만들 것이 없다.

---

### 6단계 — 판정·서술·카드·발송

```
축구 판정을 완성해라. 무승부는 1단계에서 고른 방식대로 한다.
제미니가 쓴 분석글을 그대로 카드에 싣고, 실제로 텔레그램에 보내 봐라.
```

**왜 마지막에 카드인가** — 오늘 **P0 가 정확히 여기서 났다.** 판정 4/4 가
성공했는데 카드는 "판정 부착 0건"으로 나갔다. `_render_card` 가 확률(`p_claude`)이
있어야 판정으로 세는데 v3 는 확률을 지운 경로였기 때문이다.
**판정이 되는 것과 카드가 나오는 것은 다르다.** 그래서 카드까지 가서야 끝이다.

**왜 실제로 보내 보라고 하나** — 로그의 "발송 성공"은 사용자가 읽은 것과 다르다.
오늘도 카드 전문을 눈으로 보고서야 "이건 원문 조각이지 분석글이 아니다"가 나왔다.

---

### 매 단계에 붙일 공통 지시

```
· 추측하지 말고 코드를 열어 확인해라. 측정 안 했으면 "모른다"고 써라.
· 프로브로 결함을 주장하기 전에 실제 파이프라인으로 재확인해라
  (docs/HANDOFF_2026-09-12.md §5).
· 야구 경로가 바뀌지 않는다는 것을 계약 테스트로 못 박아라.
· 완료 보고는 증거 3요소 — 테스트 수치 · 실행 시각 · 커밋 해시.
· 유료 호출 상한을 넘기지 마라 — 경기당 검색 2라운드 · 판정 2회.
```

**왜 이 다섯인가**
1. **추측 금지** — 오늘 "DB가 비었다"를 두 번 보고했다 두 번 다 틀렸다.
2. **프로브 ≠ 파이프라인** — 그 두 번의 원인이 정확히 이것이었다.
3. **야구 회귀 계약** — 축구 작업이 야구를 깨뜨리면 그게 최악이다. 사람이
   기억하는 대신 테스트가 막아야 한다.
4. **증거 3요소** — Stop 훅이 검사한다. 없으면 "완료"가 아니다.
5. **유료 상한** — x_search 가 호출당 $0.413 을 태우는 동안 **아무도 몰랐다**.
   상한이 계약으로 잠겨 있지 않으면 같은 일이 반복된다.
