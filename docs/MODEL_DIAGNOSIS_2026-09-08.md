## 0. 방법 — 경기 단위로 센다

`pick_ledger` 는 **경기당 여러 행**이다(채점행 645 / 경기 147, 경기당 4.4행).
재판정이 많은 경기가 그만큼 여러 번 세어지므로 행 단위 집계는 재판정 횟수로
가중된다. `is_final` 이 경기당 1행을 보장한다
(`idx_pick_ledger_final(game_id,date) WHERE is_final` 유니크 부분 인덱스).

⚠️ **시스템 자체 보고는 정상이다** — `calibration.py:105`·`daily_summary.py:132`
   가 이미 `l.is_final` 로 거른다. 틀렸던 것은 **감사 문서(LED-A)와 이 세션의
   첫 백테스트**였다.

| | 추천 적중률 |
|---|---|
| 행 단위 (LED-A 가 쓴 방식) | 51.4% |
| **경기 단위 (`is_final`)** | **29.4%** |

이 차이 때문에 첫 백테스트에서 `p>=0.58 · |괴리|<4 → 75.9%` 라는 수를 냈다가
경기 단위로 64.3%(n=14)로 무너지는 것을 확인했다. **그 수는 폐기한다.**

## 1. 게이트가 역방향이다 (LED-A 재확인, 더 나쁨)

```
157경기 · 기준 54.8%
  보드만      113경기  58.4%
  거부권탈락    22경기  63.6%     ← 버린 것
  추천         17경기  29.4%     ← 고른 것
  가치주의       5경기  20.0%
```
추천이 기준보다 **25.4%p 낮다**(감사는 11.1%p 로 봤다). 표본 17이라 단독으로는
유의하지 않지만 아래 §2 가 구조를 설명한다.

## 2. 확률 띠가 뒤집혀 있다 (GATE-3 재확인)

```
p 0.50–0.55  45경기  71.1%
p 0.55–0.60  54경기  40.7%   ← 추천 하한 0.58 이 이 띠 안에 있다

p 0.65–0.70  13경기  76.9%
```
0.50–0.55 와 0.55–0.60 의 격차가 **99경기에서 30.4%p**. 가장 단단한 신호다.
**임계를 옮기는 것으로는 안 고쳐진다 — 띠 자체가 뒤집혀 있다.**

뿌리는 PL-1 이다: `p_final = p_claude` 원값이고 보정도 앙상블도 없다
(docstring 은 `0.5*p_model + 0.5*p_claude` 라고 적혀 있지만 야구 분기는
`blend()` 를 부르지 않는다).

## 6-2. 라인업 확정이 주는 것은 이름뿐이다 (운영 캐시 실측)

```
today_nine.home.order = [{"slot":1,"name":"度会 隆輝","pos":"左","status":"usual"}, …]
research.home_lineup  = {"order":"度会 隆輝(左)-林 琢真(二)-…", "source":"크롤러"}

```
타율·최근 폼·좌우 스플릿이 없다. 투수 쪽과 나란히 놓으면 두께가 확연하다:
```
research.home_starter_recent = [{"opponent":"Yomiuri Giants","innings":7.0,"r":1,
  "hits":4,"k":7,"bb":0,"run_support":2,"date":"2026-09-02"}, … 5경기]
```

⚠️ `home_offense` 의 `ops`·`slg`·`avg` 는 **시즌 누적**이다. 대원칙(최근 3~5경기)
   위반 여부를 따로 확인해야 한다 — CR-1 과 같은 계열일 수 있다.

## 6-3. 그 재판정은 거의 안 움직이고, **움직일 때 틀린다**

```
확률 이동 없음(<0.01)   48경기  62.5%
작음(0.01~0.05)       77경기  53.2%
중간(0.05~0.10)       15경기  66.7%
큼(>=0.10)             7경기  28.6%

평균 이동 2.59%p · 중앙값 2.00%p · 이동이 정확히 0인 경기 42건
리그별 평균 이동: kbo 2.32%p · mlb 2.77%p · npb 2.09%p
```
**비싼 최종 판정이 확률을 평균 2.6%p 밖에 안 움직인다** — 대부분 재확인이다.
크게 움직인 7경기는 28.6%만 맞았다. §3 의 "뒤집힌 11경기 — 1차 7 / 최종 4" 와
같은 방향이다.

## 6-4. 그래서 구조가 이렇다

> 1차 판정은 **투수 재료(개인 경기별 로그 4자료)** 로 낸다 → 70.4%.
> 라인업이 확정되면 **숫자 없는 이름 아홉**이 도착하고 재판정을 촉발한다.
> 재판정은 새 숫자가 없으니 타순 **순서에서 추론**할 수밖에 없다 → 확률이 흔들린다.
> 흔들린 만큼 나빠진다(51.5%, 크게 흔들리면 28.6%).

`app/engine/CLAUDE.md` 가 그 결손을 이미 알고 있었다:
> ⚠️ **대체는 아직 못 했다.** 최근 5경기 타격은 MLB(statsapi `lastXGames`)만
> 되고 **KBO·NPB 는 경로가 없다.** 경로가 생길 때 3리그 동시에 넣는다.

NPB 가 가장 나쁜 것(39.1%)과 맞물린다.

# 8. 🔴 확률 보정 착수 — **보정으로 고칠 수 있는 문제가 아니었다**

사용자 지시로 보정을 시작했다. **곡선을 만들기 전에 "p 에 신호가 있는가"를
먼저 쟀고, 그 답이 설계를 바꿨다.**

## 8-1. 우리 확률에는 판별력이 없다

```
판별력 (AUC · 0.5 = 정보 없음)
  우리 p_home   0.519 (157경기)  ·  시장과 겹치는 120경기에서는 **0.500**
  시장 p_home   0.654 (120경기)

브라이어 (낮을수록 좋다 · 0.25 = 항상 50%로 찍기)
  우리 0.2530   ← **항상 50%라고 말하는 것보다 나쁘다**
  시장 0.2362

혼합(같은 120경기): 우리 0% → 0.654 · 25% → 0.632 · 50% → 0.594
                    75% → 0.546 · 100% → 0.500
                    **우리 비중이 커질수록 단조로 나빠진다**

리그별 우리 AUC: kbo 0.683(29) · mlb 0.492(105) · npb 0.451(23)
```

🔴 **보정은 AUC 를 바꾸지 못한다.** 단조 변환이라 순위가 그대로다. 보정이
   고치는 것은 "60%라 말했는데 실제 50%"(신뢰도 오차)이고, 지금 문제는
   "60%와 52% 중 어느 쪽이 이길지 모른다"(판별력 0)이다.
   **곡선을 어떻게 그려도 적중률은 오르지 않는다.**

즉 §2 의 "확률 띠가 뒤집혔다"는 보정 문제가 아니라 **신호 부재**의 겉모습이다.

## 8-2. 배당이 아닌 축 — 자료12(Elo)도 신호가 없었다

시장은 판별력을 갖고 있다(0.654). 그러나 `CLAUDE.md` 의 **배당 격리**가 막는다.
그래서 자료12 를 검증했다 — 경기 결과에서 Elo 를 재구성해 백테스트
(예측 시점 레이팅만 사용, 미래 정보 없음):

```
K=20 홈이점=35   145경기 AUC 0.473 · kbo 0.519 · mlb 0.449 · npb 0.408
K=20 홈이점=0    145경기 AUC 0.471
K=12 홈이점=35   145경기 AUC 0.471
```
팀 이름 표기는 깨끗하다(kbo 10 · npb 12 · mlb 30) — 그 때문이 아니다.

## 8-3. 진짜 이유 — `games` 표가 리그 이력이 아니다

```
kbo    224경기  2026-06-28 ~ 09-06     팀당 ~22경기
npb    154경기  2026-08-06 ~ 09-06     팀당 ~13경기 (한 달치)
mlb    357경기  2024-08-26 ~ 2026-09-08  ← 2년에 걸쳐 357경기
                                          (실제 MLB 는 시즌당 2,430경기)
```
`app/models/team_elo.py` 가 스스로 적어 두었다:
> 원천은 **우리 `games` 테이블뿐이다** — 외부 API 를 부르지 않는다.

**v1.4 의 근거와 어긋난다.** 그 근거는 "시장 p ↔ **시즌 실력** r=+0.707" 였는데,
지금 자료12 가 쓰는 것은 시즌 실력이 아니라 **한두 달치 조각 이력**이다.

## 8-4. ✅ 외부 API 를 부르면 해결된다 (실측)

사용자 질문 — *"외부 API를 부르면?"* **재봤다. 크게 해결된다.**


MLB **6배**, KBO **2.8배**. 그리고 **셋 다 이미 코드에 클라이언트가 있다** —
`app/collectors/mlb.py`(statsapi) · `kbo_boxscore.fetch_game_ids(season, month)` ·
`YahooNPBClient.schedule(date)`. 새 API 계약도 키도 필요 없다.

- **배당 격리를 안 어긴다** — 가져오는 것은 경기 결과지 배당이 아니다.
- **대원칙도 안 어긴다** — Elo 는 이미 "집계표가 아니라 오늘 시점 상태값"으로
  자료12 허용을 받았다.
- **PL-1(앙상블 부재)의 해법이 그때 성립한다** — 지금은 섞을 두 번째 축이
  없어서 못 섞는 것이다.

⚠️ **적중률이 오른다고 아직 말할 수 없다.** 전 시즌 Elo 의 AUC 를 실제로 재봐야
   안다. 다만 백테스트가 실패한 이유가 "Elo 가 쓸모없다"가 아니라 "표본이 팀당
   13~24경기였다"인 것은 확인됐고, 그것은 고칠 수 있는 원인이다.

## 8-5. 그래서 순서가 바뀐다

1. **리그 전체 경기 결과 적재** (backfill + 일일 증분) → 자료12 가 실력을 잰다
2. 그 Elo 의 AUC 를 **다시 측정** — 신호가 서면 앙상블(PL-1)로 간다
3. **타자 재료 신설(ⓐ)** — §6·§7
4. **그다음에 보정** — 축이 신호를 갖게 된 뒤라야 의미가 있다

⚠️ 지금 보정 곡선을 만들어 넣는 것은 낭비다. AUC 0.500 을 어떤 곡선에
   통과시켜도 0.500 이다.

## 8-6. 섬도로 지금 할 수 있는 것

보정 곡선 대신 **판별력 자체를 계속 재는 장치**가 필요하다. 지금은 AUC·브라이어를
아무도 안 본다 — 그래서 판별력이 0인 것을 오늘 처음 알았다.
`calibration.py` 가 이미 `is_final` 로 원장을 읽으므로 거기에 AUC·브라이어를
더하는 것이 가장 싸다.
